### Cause racine (démontrée par le code)

`cd-finisher.sh` purge ses artefacts à la sortie :

- `trap '… rm -f /tmp/next-build.tar.gz /tmp/cd-finisher.sh' EXIT` (ligne 48) ;
- chemin idempotent « déjà déployé + site sain » → même purge (ligne 68).

Or **le poller pull exécute le même finisher depuis les mêmes chemins
partagés** (`/tmp/next-build.tar.gz`, `/tmp/cd-finisher.sh`). Séquence du run :

1. 10:20 — le poller voit la nouvelle release, déploie (prod à jour) ;
2. le trap/idempotence **purge** `/tmp/cd-finisher.sh` ;
3. 10:21 — le SCP du CD re-transfère les fichiers (success) ;
4. ~10:22 — cycle poller suivant → purge à nouveau ;
5. 10:21→10:25 — les 4 tentatives de swap SSH tombent sur un fichier absent
   (127). Le CD rendait son verdict sur des artefacts que l'autre canal
   détruisait en parallèle.

Le flock (`deploy.lock`) sérialise bien les *exécutions* du finisher, mais
rien ne protégeait les *artefacts* entre canaux.

### Correctif — séparation complète des canaux d'artefacts

**`infra/deploy/cd-finisher.sh`** (rétrocompatible : 1 seul argument =
comportement historique identique) :

- 2ᵉ argument `TAR_PATH` (défaut `/tmp/next-build.tar.gz`) — le chemin du
  build devient paramétrable ;
- purge ciblée : `purge_canal()` supprime `$TAR_PATH` + `$0` **uniquement si
  `$0` vit sous `/tmp`** (jamais le script du dépôt si un dev l'exécute
  depuis son checkout) ;
- checksum et extraction suivent `$TAR_PATH` (`$TAR_PATH.sha256`,
  `dirname/basename` pour `sha256sum -c`).

**`.github/workflows/deploy-vps.yml`** (canal SSH du CD) :

- SCP : `mkdir -p /tmp/cd-channel` puis envoi vers
  `/tmp/cd-channel/next-build.tar.gz` + `/tmp/cd-channel/cd-finisher.sh` ;
- swap : `bash /tmp/cd-channel/cd-finisher.sh <SHA> /tmp/cd-channel/next-build.tar.gz`.

**`pull-deploy.sh`** : inchangé (défauts historiques).

Résultat : le poller peut déployer/purger à chaque cycle **sans jamais
