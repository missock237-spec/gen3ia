### 3.1 Contrats constatés (lecture des routes)

- `GET /api/extensions/installed` → `{installations: [{id, extensionId, version, status:"active", installedAt, extension:{name, category, developerName, pricing, stats…}}]}` ( Firestore : `status == "active"`, plafond 100).
- `GET /api/extensions/purchases?limit≤100` → `{purchases: [PurchaseDoc + extension]}` — `PurchaseDoc = {id, provider:"wallet"|"chariow", amountMinor, currency, status: pending|paid|failed|refunded, kind: one_time|subscription, createdAt, paidAt}`.
- `GET /api/extensions/licenses?limit≤100` → `{licenses: [{id, licenseKey, extensionId, purchaseId, status, expiresAt, createdAt, extension}]}`.
- `GET /api/extensions/usage?extensionId=…&limit≤100` → `{extension, installation, executions:[{toolId, ok, status, durationMs, createdAt, error}]}` — **403 si l'extension n'est pas installée** (le serveur est la source de vérité, l'UI restitue l'erreur telle quelle).

### 3.2 Décision d'interface

La page **constate, elle ne vend pas** : aucun appel d'achat ni d'installation (le tunnel d'achat reste Facturation / fiches catalogue — Chariow unique canal de paiement externe, règle d'or du dépôt). Les achats affichent le canal réel et le statut brut du serveur, sans adoucissement. L'usage par extension est chargé paresseusement (un clic → un GET `?extensionId=` encodé, résultat mis en cache en mémoire de session).

**Analyse.** La surveillance it.24 dispose d'un cycle d'issue complet (ouverture ROUGE → édition anti-spam → clôture RÉTABLI avec preuve) — mais il n'avait **jamais été exécuté sur une vraie dégradation** (tous les runs étaient VERTS). Le premier ROUGE réel a révélé que l'alarme était **structurellement muette** : le verdict ROUGE est bien calculé (exit 1 de la sonde), mais le reporting crashait. Un système d'alerte qui ne peut pas alerter est un faux sentiment de sécurité — exactement la famille de défaut que la garde it.29 traque côté produit, ici côté observabilité.

**Correction (double défense) :**
1. **Immédiate** : label `surveillance-prod` créé côté dépôt (couleur D93F0B, description documentée).
2. **Structurelle** (`.github/workflows/surveillance-production.yml`) : le step d'ouverture auto-répare le label de façon **idempotente** (`gh label create --force || true`) avant toute utilisation ; et si la création avec label échoue malgré tout, l'issue est créée **SANS label** — *une alarme sans étiquette vaut mieux qu'aucune alarme*. En-tête du workflow documenté (généalogie de l'incident).
3. **Verrou** (`tests/unit/surveillance-production.test.ts`, 12e test) : le step d'ouverture doit contenir l'auto-réparation ET le secours sans label — une régression du canal d'alarme sera rouge en CI.

**Preuve post-correctif** : `workflow_dispatch` manuel de la surveillance → **success** (13:56Z) ; le run couplé du CD (13:50Z) également VERT. Le pic TTFB `health` post-swap reste un phénomène réel à observer (déjà 3 observations : it.29 502, it.30 latence 21 min, it.31 TTFB) — voir §9.
