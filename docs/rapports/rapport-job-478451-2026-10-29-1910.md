## 3. Audit systématique — du motif « code mort » à la garde structurelle

### 3.1 Méthode

Répétition du schéma d'audit des itérations précédentes : inventorier l'existant, croiser avec les usages réels, mesurer l'écart. Ici : (1) énumérer tous les `app/api/…/route.ts` (302 endpoints) ; (2) charger la **surface utilisateur** — `app/` hors `app/api/`, `components/`, `public/`, `middleware.ts`, `next.config.*` (237 fichiers) — seul lieu où une route devient accessible à quelqu'un ; (3) chercher chaque endpoint (préfixe statique, coupe avant les segments dynamiques) dans ces fichiers ; (4) croiser les orphelins détectés avec une recherche repo-wide pour distinguer « appelé côté serveur via lib/ » de « réellement mort ».

### 3.3 Root cause (récurrente depuis it.22)

Le pipeline « endpoint + tests verts + build OK » ne vérifie jamais qu'**un être humain peut atteindre la fonctionnalité**. Chaque lot ajoute ses routes backend ; la surface UI est une décision séparée, souvent oubliée ; aucun signal automatisé ne l'alerte. Comme pour l'étanchéité art. 17 (it.27 : invariant structurel plutôt que liste), la réponse est une **garde structurelle**, pas un nettoyage ponctuel.

## 4. Correctifs et évolution (commit `7a20723`)

### 4.1 La garde — `tests/unit/api-endpoints-dead-code-guard.test.ts` (6 tests)

1. **Auto-protection** : planchers 250 endpoints / 200 fichiers UI — si le walker casse, la garde devient vacuole (0 orphelin = tout passe) ; les planchers rendent cette défaillance visible. Inclut une route dynamique `[id]` pour vérifier la gestion des segments variables.
2. **Structure** : chaque `route.ts` doit exporter au moins un gestionnaire HTTP (GET/POST/…) — attrape le code mort pur.
3. **Cœur de la garde** : tout endpoint **sans référence UI ET hors baseline** fait échouer la CI avec un message actionnable (« câbler l'UI, ou documenter une entrée motivée »). La 5e occurrence du motif devient impossible à livrer sans décision explicite.
4. **Hygiène baseline (prune)** : une entrée de baseline devenue référencée doit être retirée — le registre ne peut pas gonfler en silence.
5. **Égalité ensembliste** : baseline = exactement les orphelins calculés (ni registre fantôme, ni trou) + anti-doublons.
6. **Exigence RGPD** : `/account/export`, `/auth/account`, `/memory/export`, `/memory/purge` doivent rester câblés à l'UI et **ne jamais rejoindre la baseline** — régression it.25/it.27 impossible.

La baseline (102 entrées, classées par motif, chaque catégorie documentée) est un **registre honnête**, pas une liste blanche paresseuse : elle se prune toute seule (règle 4) et refuse ses propres fantômes (règle 5) — la même école que le manifeste honnête it.25/it.27.

### 4.2 Boucle fermée le jour même — `/api/settings/export-data` câblé

La garde confirmait l'orphelin it.27 : l'export des paramètres existait, testé, déployé… sans bouton. `components/settings/data-governance-section.tsx` (créé it.25) expose désormais un troisième bouton **« Exporter les paramètres »** → `GET /api/settings/export-data` → téléchargement `gen3ia-parametres-<horodatage>.json` (format `gen3ia.settings-export` v1, manifeste honnête inclus). Même pattern `authFetch`/`telecharge`, tokens `g3-*` existants, `aria` conservé. La baseline passe 103 → 102 **sous la contrainte du test d'hygiène** — la garde démontre sa boucle : détecter → câbler → élaguer.
