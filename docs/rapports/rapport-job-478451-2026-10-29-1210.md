## 3. Analyse détaillée — faille de résilience runtime

### 3.1 Constat (audit résilience, domaine non encore couvert par les itérations 15–21)

L'arborescence App Router présentait une asymétrie remarquable : **neuf segments** (`app/neural`, `app/dashboard`, `app/settings`, `app/team`, `app/developer`, `app/admin`, `app/live`, `app/billing`, `app/memory`) disposent d'un `loading.tsx` soigné (skeletons thématisés), mais **aucun ne possédait d'`error.tsx` segmentaire**. Dans l'App Router de Next.js, sans `error.tsx` au niveau du segment, une exception de rendu — crash synchrone dans un composant client, donnée inattendue au rendu, erreur d'hydratation fatale — se propage au parent le plus proche disposant d'une boundary : ici la racine `app/error.tsx`. Conséquence utilisateur : la page entière est substituée par l'écran d'erreur global, la sidebar et la navigation disparaissent, alors que seul un panneau était cassé.

### 3.2 Anomalie associée : composant `ErrorBoundary` mort

`components/error/ErrorBoundary.tsx` (boundary de classe, capture Sentry avec `componentStack`, `resetKeys`, fallback personnalisable) existait depuis le commit `6069ca4` mais n'était **importé nulle part** — ni dans `app/`, ni dans `components/`, et aucun test ne le couvrait. Un composant de résilience non branché n'apporte aucune résilience ; il ne restait que son poids de maintenance.

### 3.3 Ce qui était déjà solide (et a été conservé tel quel)

- `app/error.tsx` et `app/global-error.tsx` : boundaries racines thématisées, digest affiché, capture via le pont Sentry asynchrone (`captureClientException`, zéro kB au chemin critique, mesure ADR-005) — le `global-error` rend son propre `<html>` avec bootstrap de thème localStorage.
- Capture `window.onerror` + `unhandledrejection` dans `lib/telemetry/sentry-bridge-client.ts` (captée au niveau capture phase, nettoyée aux tests).
- Pages défensives sur le plan *données* : `app/admin/page.tsx` gère déjà états de chargement et erreurs de fetch (try/catch), mais rien ne protégeait le *rendu* lui-même.

## 4. Corrections livrées (commit `603534e`)

### 4.1 `components/error/segment-error.tsx` — composant partagé

Boundary d'affichage réutilisable consommée par les neuf `error.tsx` segmentaires : icône et carte thématisées exclusivement via tokens `--g3-*` (sombre/clair automatiques), eyebrow `Gen3ia · <segment> · erreur inattendue`, titre et message **contextuels par segment**, digest Next affiché en `<code>` pour corrélation support ↔ Sentry, `role="alert"` (WCAG 4.1.3 status messages), bouton **Réessayer** (`reset` natif Next) et lien de retour contextuel. Capture Sentry via le pont asynchrone uniquement — aucun import direct `@sentry/nextjs` (le garde-fou l'interdit désormais), tags `surface="segment-error"`, `segment`, `digest`.

### 4.2 Neuf `app/<segment>/error.tsx` générés (`scripts/gen_segment_errors.mjs`)

Chaque fichier est un wrapper minimal (~30 lignes) qui passe au composant partagé le tag de segment et un message rassurant spécifique (« Vos conversations et vos agents restent intacts… », « Vos abonnements et vos paiements restent intacts… », etc.). Effet mécanique : le crash est **contenu au segment** — le layout racine, la navigation et les segments voisins restent vivants ; le bouton Réessayer re-rend uniquement le segment.

### 4.3 Containment granulaire dans `app/admin/page.tsx`

La console d'administration isole désormais ses deux zones par `<ErrorBoundary fallback={ZoneFallback}>` : la **grille de métriques** (8 `MetricCard`) et la section **Missions par statut**. Un crash de rendu dans l'une (ex. `data.metrics[key]` inattendu) n'emporte plus l'autre — `ZoneFallback` affiche un bandeau `role="alert"` compact avec un bouton Réessayer qui re-rend la seule zone affectée. Le composant `ErrorBoundary` passe ainsi de l'état de code mort à un branchement de production documenté (et transmet `componentStack` à Sentry pour le diagnostic).

### 4.4 Garde-fou structurel — `tests/unit/segment-error-boundaries.test.ts` (17 tests)

- Les 9 segments possèdent un `error.tsx` branché sur `SegmentError` avec le bon tag, les props Next typées (`error + digest?`, `reset`).
- Tout segment à `loading.tsx` doit avoir un `error.tsx` (filet pour les segments futurs).
- `SegmentError` : pont asynchrone obligatoire, `@sentry/nextjs` direct interdit, `role="alert"`, digest, composant `"use client"`.
- Page admin : au moins deux `<ErrorBoundary>` avec fallback accessible.
- Filets racines intacts : `app/error.tsx` + `app/global-error.tsx` toujours présents, `global-error` toujours autonome.
