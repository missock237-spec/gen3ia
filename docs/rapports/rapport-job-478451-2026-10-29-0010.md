## 4. Anomalie détectée et corrigée : `/api/media/professeur-statut` renvoyait 500 au lieu de 401

### Découverte

Sondage des endpoints IA de production : `/api/essaim/etat` sans jeton renvoie un **401 JSON
propre** (`{"success":false,"error":"Authentification requise…"}), mais
`/api/media/professeur-statut` renvoyait **HTTP 500 avec corps vide** dans la même situation.

### Cause racine

La route appelait `await requireUser(request)` **hors de tout try/catch** : le
`HttpError(401)` lancé par le socle d'authentification se propageait jusqu'à Next.js, qui
convertit une exception non gérée en 500 vide. Toutes les autres routes (115 fichiers
`route.ts` utilisant `requireUser`) enveloppent l'appel dans l'idiome maison
`try/catch → errorBody/errorStatus/errorCode` — un scan systématique (script
`scripts/scan_requireuser_500.py`, heuristique try/catch sur chaque appel) a confirmé que
`professeur-statut` était **la seule route touchée**.

### Correctif (commit de cette itération)

- `app/api/media/professeur-statut/route.ts` : enveloppement de `requireUser` dans le
  filet maison (`catch → NextResponse.json(errorBody(error), { status: errorStatus(error),
  headers: { "x-gen3ia-error-code": errorCode(error) } })`), commentaire expliquant le bug.
- Validation locale : `npm run typecheck` **exit 0** (sandbox réinstallé, dépendances
  complètes), `eslint` sur le fichier **exit 0**.
- Impact utilisateur : les clients authentifiés ne voient aucun changement ; les clients
  non authentifiés et la surveillance reçoivent désormais le 401 sémantique attendu
  (plus de faux 500 dans les métriques d'erreur).

### Pourquoi ce 500 n'était pas une panne de production

Le diagnostic de la route n'expose aucun secret et l'erreur ne touchait que les appels
sans jeton (le navigateur des utilisateurs connectés passe l'auth). Mais un faux 500 sur
une route documentée fausse les SLO/moniteurs — il a été corrigé en conséquence.
