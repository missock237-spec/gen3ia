## 4. Réalisation (commit `8ffaa3c`)

### 4.1 Tables secondaires — extension configuration-driven

- `ModuleDef` étendu d'un champ optionnel `secondaire: {recordsKey, libelleCle, titre, colonnes}` — les 4 modules du lot 1 restent à une seule table (zéro changement comportemental).
- Extraction : la correspondance serveur (`Record`) devient des lignes via `Object.entries(...)` + **spread des valeurs telles quelles** — transformation structurelle, aucune valeur recalculée (le champ `libelleCle` reçoit la clé, ex. « Employé »).
- Rendu : h3 + table native (th scope) + même troncature honnête que la table principale (8 lignes + compteur du total). Si la liste principale est vide alors que la secondaire existe (ex. registre RGPD rempli, aucune DSR), l'état « pret » est conservé et un message dédié évite une table à corps vide — cas impossible pour les modules du lot 1 (comportement inchangé).

### 4.2 Honnêteté KPI et format « taille »

- `hr-leaves` : `kpis: []` — le serveur ne calcule pas d'indicateur, aucun n'est inventé ; la grille KPI n'est rendue que si `module.kpis.length > 0`.
- `compliance-gdpr` : KPI `openRequests` (« Demandes ouvertes ») et `breached` (« SLA dépassé ») affichés tels quels ; `onboarding` : `total/active/completed`.
- Nouveau format de colonne `taille` : `Array.isArray(brut) ? String(brut.length) : "—"` — comptage **structurel** d'une liste serveur (étapes d'un parcours), documenté dans la source comme « jamais un calcul métier ».
