## 4. Amélioration évolutive — Guérisseur v6.2 (commit `12b8de4`)

### 4.1 Le principe : le secours ne peut pas être SSH

Constat fondateur : quand SSH entrant est muet ET poller silencieux, les deux canaux historiques sont morts. Or l'opérateur-agent a rétabli la livraison en **un dispatch CD** — car chaque runner GitHub a une IP egress différente. Le guérisseur doit savoir faire ce que l'opérateur a fait à la main : c'est le **renouvellement d'IP runner**.

### 4.2 Étape « Secours sans SSH — redéclencher le CD »

- **Conditions conjonctives strictes (anti-spam)** : sonde SSH muette **ET** `release_sha == sha_main` (release prête, inutile de re-builder autre chose) **ET** âge release ≥ 10 min (le poller a eu ses 5 cycles de 2 min — même seuil que le watchdog v6.1 ; avant, le poller normal a la priorité).
- **Action** : `gh workflow run deploy-vps.yml` — sérialisé par la concurrency du CD, exécution ~6–8 min, puis swap SSH à IP neuve ou release re-publiée.
- **Observabilité** : le rapport du tick trace `secours-ip = success/skipped` — un opérateur lit le verdict sans décompiler les étapes.

### 4.3 Garde d'escalade anti-race

L'escalade v6.1 vérifie « CD en cours » via l'API — mais un run dispatched n'apparaît pas instantanément (latence API) : escalader le même tick où le secours vient de s'armer = faux positif garanti. Le garde v6.2 : **si `secours-ip.outcome == 'success'`, pas d'escalade ce tick** — le prochain tick jugera le résultat (escalade = preuve d'échec en chaîne, pas d'impatience).

### 4.4 Garde-fous

`lib/__tests__/ci-pipeline.test.ts` (+2 tests, 29 au total sur le fichier) : conditions conjonctives des trois gardes verrouillées (muette + release à jour + âge ≥ 10), dispatch CD explicite (pas d'appel SSH direct dans le secours), traçabilité dans le rapport, garde anti-race présent. YAML revalidé, `node --check` implicite via les tests existants.
